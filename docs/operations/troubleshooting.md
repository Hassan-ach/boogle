# Troubleshooting

**Last updated:** 2026-11-23

Start with the basics: `docker compose ps`, `just run-logs`, and the check table in [Monitoring](monitoring.md#what-an-operator-can-check-today). Remember that a "healthy" container only proves liveness in three of the four services, and that `/health` is database-agnostic.

!!! note "Finding labels"
    Items marked **review finding** come from `project-review-2026-11-22.md`. They were verified against source (and, for H-01, reproduced with a probe) but are not fixed by this documentation. Track them in [Known issues](../reference/known-issues.md).

## Symptom / cause / check / action

| Symptom | Likely cause | Check | Action |
|---|---|---|---|
| **No results after a crawl**, including for a phrase that was previously found | **X-01 (review finding, HIGH):** on re-crawl, spider's upsert updates only `metadata` — `html`, `indexed`, `indexed_at` stay unchanged; the indexer claim requires `indexed = FALSE`, so the new job is rejected as "already indexed" | In Adminer, inspect the `pages` row for that URL (`html`, `indexed`, `indexed_at`); check spider logs for the published job and indexer logs for a not-found/already-indexed response | No configuration workaround. Confirm this is a re-crawl, not a first crawl; for first crawls, verify the spider → indexer → ranking path. Follow the fix in [Known issues](../reference/known-issues.md). |
| **Crawler silently skips a whole host**; no obvious error in logs | **H-01 (review finding, HIGH):** a 404/403 response for `/robots.txt` is converted to a generic fetch error, marks the host dead, and `hostGate` skips every URL on it until the dead-host TTL expires | Fetch the seed host's `/robots.txt` and note its status; search spider logs for host-dead/skip markers | Temporary workaround: make seed hosts serve a valid `200` robots.txt. Permanent fix is a spider code change — see [Known issues](../reference/known-issues.md) and the [Spider service](../services/spider/index.md). |
| **Multi-word searches return zero results, single words still work** | **H-03 (review finding, HIGH):** aspell initialization failed at engine startup, so the silent `DummySpeller` fallback returns the entire joined phrase as one term, while indexed `words.word` values are single tokens | Compare a one-word and a multi-word query. There is **no log signal** for the fallback, so absence of an error does not rule it out; confirm the engine image's `aspell aspell-en` install and runtime locale | Restore the dictionary/locale or rebuild the engine image. Track the fix in [Known issues](../reference/known-issues.md); see [Engine service](../services/engine/index.md). |
| **Engine is reachable from outside the host; rate limit appears ineffective** | **H-02 (review finding, HIGH):** `1323:1323` binds all host interfaces; Echo's in-process limiter derives identity from forwarding headers that an unauthenticated client can rotate. No auth or TLS exists | Read `services/engine/docker-compose.yml` port binding; check which interfaces port 1323 is listening on | Restrict access at the host firewall or rebind the port to loopback for local use. A reverse proxy alone does not fix spoofed client identity. See [Known issues](../reference/known-issues.md). |
| **Services fail at startup** ("... is not set") or engine restart-loops | Missing required env vars in an entrypoint, or engine's DB pool ping failed at boot (it pings Postgres with a 10s timeout and exits on failure) | `just env` output; variable names in root `.env` and `services/*/.env`; `docker compose ps`; `docker compose exec -T psql pg_isready -U "${PG_USER:-admin}"` | Fix the `.env` values, run `just env` to regenerate overlays, then `just stop && just run`. Note that this also restarts Redis, which has no persistent volume. |
| **Cannot log in to Adminer or RabbitMQ Management UI** | Adminer uses the Postgres credentials (`PG_USER` / `PG_PASSWORD`); RabbitMQ uses `RABBITMQ_DEFAULT_USER` / `RABBITMQ_DEFAULT_PASS` from the root `.env`. Neither UI has a preconfigured login in Compose | The corresponding values in the root `.env`; for the broker also check the spider overlay's `RABBITMQ_USER` / `RABBITMQ_PASSWORD` | Edit the root `.env`, re-run `just env`, restart the root stack with `just stop && just run`. Both UIs are loopback-only (`8080`, `15672`). |
| **`indexer.jobs` queue depth keeps growing** | Indexer is down, restarting, or failing DB writes; claims may be stuck open until the sweep reclaims them (`SWEEP_INTERVAL_SECONDS`, `SWEEP_GRACE_SECONDS`) | RabbitMQ UI at `http://127.0.0.1:15672`; `docker compose ps`; indexer logs; Postgres connectivity via the `pg_isready` check above | Restore indexer and fix its DB/broker connection first. Avoid unnecessary Redis restarts (frontier state is not persisted). See [Indexer service](../services/indexer/index.md). |
| **`indexer.confirmations` grows but rankings never change** | Ranking runs at startup and only when the confirmation threshold is reached (default `RANKING_CONFIRMATION_THRESHOLD=100`); there is no wall-clock scheduler. Review finding M-18 notes no retry after a failed run | RabbitMQ UI queue depth; ranking logs for a started/failed pipeline run; engine results for a known ranked term | Index more pages to cross the threshold, or restart ranking to force its startup run (`RANKING_RUN_ON_STARTUP`, default true). Investigate any ranking failure before assuming it is merely idle. See [Ranking service](../services/ranking/index.md). |
| **Port 1323 conflict: `just run` fails to build/start the engine** | A local `go run`/`air` engine process already owns the port | `just preflight` — it prints `port 1323 is already in use; stop the local engine/air process first` when `ss` sees the port and no `engine` container is running | Stop the local process, then `just run`. The preflight is only active when `ss` is installed. |
| **Migrations missing or schema errors after an update** | Postgres init scripts run only against an empty `PGDATA`; `scripts/migrate.sh` was not run, or `psql` was not up when it was | `just migrate` output; `docker compose ps --status running --services` must list `psql`; inspect the expected tables in Adminer | With `psql` running, run `just migrate`. Migrations are idempotent and safe to re-run (there is no tracking table). See [Migrations](../data/migrations.md). |
| **Container reports healthy but the application is broken** | Healthchecks are liveness-only: `pidof` for spider/indexer/ranking and a static `/health` response for the engine | `docker compose ps` plus the real dependency checks: `docker compose exec -T psql pg_isready -U "${PG_USER:-admin}"`, `docker compose exec -T rabbitmq rabbitmq-diagnostics -q ping`, and a `/search` request | Treat container health as "process up", not "system working". Investigate logs and the dependency checks above. |
| **Crawl frontier resets after a Redis restart** | Redis has no volume and no `appendonly` configuration in `docker-compose.yml`; `just infra-up` does not wait for Redis either | Root `docker-compose.yml` Redis service (no volumes); logs from the first crawl after restart | Re-seed/re-crawl as needed, and check X-01 above before expecting changed pages to be re-indexed. Adding persistence is a configuration change, not a shipped feature. |
| **Spider/indexer JSON log files vanished** | Both write inside the container; no host mount exists | `services/spider/.env.docker` (`LOGS_PATH=/app/logs/logs.json`) and `services/indexer/entrypoint.sh` (`LOG_PATH` default `./logs/indexer.log`); [Logging](logging.md#streams-and-files) | Use Docker's captured console stream (`just run-logs`, `docker logs`) as the durable-enough source while the container exists. Mount a host directory if files must survive removal. |

## Escalation path

1. Confirm the process is up and dependencies answer: [Monitoring](monitoring.md#what-an-operator-can-check-today).
2. Read the relevant service console output: [Logging](logging.md#where-to-look-first).
3. Reproduce against the owning service page: [Spider](../services/spider/index.md), [Engine](../services/engine/index.md), [Indexer](../services/indexer/index.md), [Ranking](../services/ranking/index.md).
4. Check whether the symptom is a documented defect: [Known issues](../reference/known-issues.md). Runbook commands are listed in [Commands](../reference/commands.md).
